# POPO Finder — 開放決策紀錄(Open Decisions)

> 這份文件記錄 [`product-direction.md`](product-direction.md) 那次方向定盤**之後**,陸續做出的個別產品決策與理由。
>
> **目的:每次要做新的產品決策前,先回顧這裡,避免前後矛盾、避免重複推導已經想過的事。**
>
> 規則:
> - 新決策往下**追加**,不要改寫歷史。
> - 若推翻舊決策,**不要刪除**原條目;把它的狀態改成「🔁 已推翻」,註明推翻的日期與原因,再新增一條對應的新決策。
> - 最高準則仍是那把尺:**「如果全世界只有 3 個人用,它對那 3 個人還有價值嗎?」** 以及 `product-direction.md` 第 5 節的倫理鐵律。

每條格式:`編號 — 標題`、日期、狀態(✅ 採納 / ❌ 否決 / ⏳ 延後 / 🔁 已推翻)、決策、理由。

## OD-1 — 「查波波就推薦替代醫師」否決,改為中性可瀏覽字典

- **日期**:2026-06-09
- **狀態**:❌ 否決(push 版);✅ 採納(pull 版,中性可瀏覽字典)
- **決策**:不做「使用者查到某醫師是波波時,主動推薦附近同科別非波波醫師」這種**情境式推薦(push)**。改為:字典本身可依**科別 + 地區**瀏覽/搜尋,讓病人**自己探索(pull)**。
- **理由**:
  - push 版撞上倫理鐵律 1(平台不下結論,判斷留給病人)——一查波波就塞替代名單,等於平台大聲說「這個別找、找這些」。
  - 也撞上鐵律 2(暗示判斷=訴訟磁鐵)——在病人查某具名醫師的當下把流量導向「替代品」,近似主動損害其執業,法律風險比單純呈現學歷高一個數量級。
  - 精神上接近第 4 節已否決的「信號/unraveling 引擎」。
  - pull 版價值幾乎相同,但平台只是讓字典可瀏覽,不下任何結論。

## OD-2 — 資料模型:一張表,存學歷事實,不存「is_popo」判斷

- **日期**:2026-06-09
- **狀態**:✅ 採納
- **決策**:波波與非波波都放在同一張 `medical_personnel`,差別只在 `education` 內容、`source`、`verification_status`。**不建立 `is_popo` 之類的判斷欄位,也不拆「波波表/非波波表」。**
- **理由**:
  - 表裡只存**可查證的事實**(學歷=台大 / 學歷=某外國醫學院 / 尚未提供)。「波波與否」永遠是病人從事實**自己推論**,平台不在資料層下結論——這是倫理鐵律 1 在 schema 上的實作。
  - 若有 `is_popo` 欄位,一旦分類錯,等於平台具名指控某醫師是波波,直接撞鐵律 2。
  - 拆表本身就是把判斷烤進架構。

## OD-3 — 「病人正面反應/回饋」:方向採納,但延後

- **日期**:2026-06-09
- **狀態**:⏳ 延後(方向採納,現在不建)
- **決策**:未來讓病人能對醫師做正面反應,形狀定為:**已驗證病人 + 結構化標籤(如「解釋清楚」「候診短」)+ 對所有醫師一視同仁(不分波波/非波波)**。但**現在不建**,要等中性字典、資料覆蓋率、以及「醫師本人具名/病人已驗證」的驗證能力先到位。
- **理由**:
  - 動機有兩個且同向:① 對病人的**可信度**(文件原本的切入點)② 對醫術好的波波的**公平**(本次新增,呼應鐵律 2「不是抓波波」)。兩者收斂到同一機制。
  - 槓桿是「**驗證留評者真的看過診**」而非「開放/擋負評」——這正是 POPO Finder 的本命能力,也化解第 4 節的可信度悖論。
  - **絕不能做**第 4 節點名的中間路:「開放大家留、但偷偷只顯示好的」(低可信 + 可灌水 + 不誠實)。
  - 評價類無論哪條路都**不是地基**,要在核心驗證與覆蓋率之後才做(見 [`product-direction.md`](product-direction.md) 第 4 節補充)。

## OD-4 — 醫師認領未上線前,UI 不顯示「驗證狀態」,「學歷佐證」語意保留給未來

- **日期**:2026-06-10
- **狀態**:✅ 採納
- **決策**:在醫師認領/本人上傳學歷證明的機制實作之前,flex 卡片**不顯示「驗證狀態」這一列**;同時把原本掛在 SourceURL 上的「**學歷佐證**」欄位標籤改名為中性的「**來源連結**」。`verification_status` 欄位與資料保留,只是先不渲染。
- **理由**:
  - 目前每筆資料的 `verification_status` 多為 `unverified`,卡片顯示「驗證狀態:尚未查證」會讓人**誤以為整個資料庫都未經查證**,比不顯示更糟、且不誠實——撞倫理鐵律「誠實標示驗證程度」。驗證狀態要等真的有「醫師本人具名/病人已驗證」的能力(見 [[OD-3]])再接回來才有意義。
  - SourceURL 目前來自 blog/民眾回報,本質是**資料來源連結**,不是經查證的學歷證明。叫「學歷佐證」等於**過度承諾**。「學歷佐證」這個語意**保留**給未來醫師上傳本人學歷證明(眾包校對/認領)時才用,屆時才是真正的佐證。

## OD-5 — 查詢紀錄(search_log):存查詢內容,不存使用者

- **日期**:2026-10-12
- **狀態**:✅ 採納
- **決策**:新增 `search_log` 表,記錄每次使用者發起的查詢(時間、查詢類型、城市、查詢字串、結果筆數),翻頁不記。**不存 LINE userId,也不存它的雜湊。**
- **理由**:
  - 定盤說價值來自覆蓋率與正確性([`product-direction.md`](product-direction.md) 第 1 節),但目前量不到「查不到的比例」,也不知道「查不到的是誰」。stdout log 隨 pod 重啟消失,無法累積。
  - 存查詢字串才分得出是「語法打錯」還是「名單裡沒有」——後者就是覆蓋率缺口。
  - 不存使用者,避免留下「某個人查過哪些醫師」的關聯;代價是算不出回訪率。可以接受:回訪不是「3 個人也有價值」這把尺的成功定義。

## OD-6 — 預設全欄位查詢、姓名符合優先;onboarding 範例不用真實醫師全名

- **日期**:2026-10-12
- **狀態**:✅ 採納
- **決策**:沒加 `@醫院`/`@科別` 時同時比對姓名、醫院、科別,排序為姓名符合 → 醫院符合 → 科別符合,摘要列出各組筆數;`@` 語法保留為精確篩選。Quick Reply 範例只用姓氏(陳)、醫院簡稱(三總)、科別(牙科),沿用原說明卡的範例。
- **理由**:
  - 第一次使用的人直接輸入醫院名,會被當成姓名查而得到 0 筆。2026-10-12 用部落格 1476 筆資料模擬:1033 個全名查詢有 1032 個結果不變,會混在一起的主要是單一姓氏(例如「林」多出林口長庚等醫院 33 筆),用姓名優先排序加分組摘要就能讓使用者看懂。
  - 不另外保留「`[城市] 姓名` 只查姓名」的舊行為:姓名符合排最前面,舊結果完整留在前段,只是後面多接醫院/科別符合的列(單一姓氏:陳 +17、林 +33、王 +4、李 +2、張與黃 +0)。要完全一致只有兩條路:一是猜輸入是不是人名(「三總」和人名從字面分不出來);二是「有姓名符合就只顯示姓名」,但它在 1684 個簡短查詢中會把 6 個查詢的醫院/科別結果藏起來,最嚴重的是「牙醫」——一筆姓名欄被誤填成「牙醫」的資料會蓋掉 395 筆牙醫診所。
  - 範例按鈕若用真實醫師全名,等於在每個新使用者面前點名某位醫師,違反倫理鐵律 1、2(中性呈現、不暗示判斷)。

## OD-7 — 主動爬醫院/診所官網,收錄所有寫了學歷的醫師(不分國內外畢業)

- **日期**:2026-10-12
- **狀態**:✅ 採納
- **決策**:
  - **目標**:讓 bot 查得到大部分在網路上公開了學歷的醫師——不只名單上國外學歷的醫師,也包括國內醫學系畢業的醫師。
  - **以醫院/診所為單位寫爬蟲**:逐家抓官網的醫師介紹頁,頁面上寫了學歷的醫師就收錄。每月重爬;頁面上消失的醫師刪除,異動由 `medical_personnel_history` 記錄(OD-8)。先後順序依盤點結果決定,先做醫學中心。
  - **只收寫了醫學學位的醫師**:頁面沒有學歷,或只寫研究所/經歷、沒寫醫學系/牙醫學系等醫學學位的,不收。在查波波的 bot 裡放「學歷:未提供」的卡片,會讓人往壞處猜(倫理鐵律 1)。
  - **只存事實**:姓名、醫院、科別、學歷、官網連結(`source_url`)、爬到的日期(`source_checked_at`),`source` 記為 `hospital_directory`(沿用 0003 的值,醫院與診所官網都用它,不另增 `official_site`)。不轉錄其他頁面文字。
  - **與名單重疊時各自存一筆**:同一位醫師同時出現在部落格名單與官網時不合併,兩張卡片分別標示來源,平台不判斷哪一筆才對。
  - **下架機制要在第一批爬蟲資料上線前完成**(倫理鐵律 4):這會一次放上大量從沒同意過的具名醫師。
  - `verification_status` 不因官網資料而改變:「官網公開」由 `source` 表達,`self_reported`/`verified` 的語意保留給醫師認領(OD-4)。
  - 名單醫師的個別校對(找現職、人工確認身分)降為輔助,不是主要的擴充方式。
  - **具名的爬取與校對結果只存在 DB,不寫進 repo**:repo 是 public,git 歷史無法下架,違反倫理鐵律 4。盤點文件只寫來源層級與數字。
  - **「禁止轉載」的網站照樣收錄,卡片顯示學歷原文+官網連結**:多數醫院首頁依《醫療機構網際網路資訊管理辦法》第 4 條聲明「禁止網際網路服務業者轉錄其網路資訊之內容供人點閱」,只允許以搜尋或超連結進入醫院網址直接點閱;各院頁尾也常寫「請勿轉載」。顯示原文可能構成轉錄——使用者 2026-10-12 知情後仍決定顯示原文(另一個選項是卡片只放「官網有公開學歷,點此查看」)。風險由下架機制承接:院方要求時整院下架。
  - **院方明確不歡迎的網站不爬**:robots 禁止(奇美主站全站 `Disallow: /`、義大封鎖 Go 預設 UA)、條款禁止儲存(中國附醫)、Cloudflare 擋住(北榮、三總)的一律不收,也不繞過;要收須先取得院方同意。爬蟲使用可識別的 UA(含聯絡網址),遵守 robots.txt 與 `Crawl-delay`。盤點見 [`sources/medical-center-inventory.md`](sources/medical-center-inventory.md)。
- **理由**:
  - [`product-direction.md`](product-direction.md) 第 3 節第 2 點本來就允許「爬更多來源(診所官網、公開學經歷等)」來提高覆蓋率;價值來自覆蓋率與正確性(第 1 節)。
  - 2026-10-12 抽樣 14 位名單醫師(見 [`sources/official-pages-inventory.md`](sources/official-pages-inventory.md)):以「名單醫師」為單位很難——要找醫師現在在哪、分辨同名,14 位只有 4 位能用官網確認學歷(0 位矛盾),而且名單的醫院欄大多過期。但以「醫院」為單位時,頁面本身就寫了「這位醫師、在這家醫院、學歷是什麼」,不需要比對身分;抽樣中有醫師介紹的頁面多半寫了學歷(義大新陳代謝科 11/16、牙科部 17/18、大里仁愛醫院乳房外科 4/4)。
  - 規模:113 年評鑑後有 23 家醫學中心;台南市 2022 年統計,西醫師 62.7% 在醫院執業、牙醫師 82.8% 在診所。爬醫院能涵蓋相當比例的西醫師,牙醫診所是長尾。
  - 不先「請醫師主動公開」:2024-11 公開學歷的爭議中,醫師公會全聯會理事長稱公開學歷「如同獵巫」、衛福部表示不會要求公開學歷,醫界至少是分裂的;而且自願公開的多半是台灣畢業的醫師,沒公開的人依鐵律 1 不能做任何暗示。醫院/診所官網已自行公開的學歷是現成的公開資料,醫療法第 85 條也允許醫療廣告登載學歷。
  - 本條初稿(同日)寫成「半自動校對名單醫師、不做全自動爬蟲」,把使用者「主動爬醫院/診所頁面、國內外畢業都收」的意圖縮小了;在 PR #37 合併前改寫為本版。

## OD-8 — 資料異動歷史表;下架時連同歷史清除

- **日期**:2026-10-12
- **狀態**:✅ 採納
- **決策**:
  - 新增 `medical_personnel_history`,由 DB trigger 記錄 `medical_personnel` 每一次 INSERT/UPDATE/DELETE(含手動 SQL):修改前後整列(JSONB)與原因;內容沒變的 UPDATE 不記。
  - 批次修改前,在交易內先 `SET LOCAL popo.change_reason = '<原因>'`,`reason` 欄記下原因(例如「資料清理:臺→台」「官網校對」)。
  - **下架時**,在同一個交易內:刪除主表那一列 → 刪除該 `personnel_id` 的全部歷史 → 寫一筆不含內容的紀錄(`op='DELETE'`、`old_row`/`new_row` 為 NULL、`reason='takedown'`)。下架機制本身(收件、流程)尚未實作;本條只規定歷史表的設計不能讓下架做不到(`personnel_id` 不設 FK、`old_row`/`new_row` 可為 NULL),由 `TestHistoryAllowsTakedownPurge` 釘住。
  - TRUNCATE 不會觸發 row trigger、不留紀錄;production 不對 `medical_personnel` 下 TRUNCATE。
  - 2026-10-12 補註:收件管道與處理方式(`SELECT takedown_personnel(<id>);`)見 OD-9。
  - 2026-10-12 補註:只改 `source_checked_at`/`updated_at` 的 UPDATE 也不記歷史(每月重爬更新查到日期),見 OD-10。
- **理由**:
  - 之後的資料清理與官網校對都用 SQL/腳本修改,server 本身不寫這張表,只有 DB trigger 抓得到所有修改路徑;沒有歷史就無法事後比對「改了什麼、為什麼改」。
  - 歷史表保留完整資料,若下架只刪主表,醫師的資料仍留在歷史表,等於沒有下架(倫理鐵律 4)。留一筆不含內容的紀錄,仍看得出「這裡曾下架一筆」。
  - 整列存 JSONB:之後主表加欄位,trigger 與歷史表都不用改。既有資料不做初始快照:每列第一次被修改時,`old_row` 就記下修改前的狀態。

## OD-9 — 下架管道:寄信+本人或院所證明,不在 bot 放下架按鈕

- **日期**:2026-10-12
- **狀態**:✅ 採納
- **決策**:
  - 醫師本人或院所要求下架或更正資料,寄信到 `jerrychuang@jerrytech.me`。說明卡(加好友與「幫助」共用)寫明信箱與證明方式。
  - 申請要附本人或院所證明(例如以院所官方信箱來信,或附上可證明是醫師本人的資料),由維護者人工判斷是否照辦。
  - **不在醫師卡片放「要求下架」按鈕,也不做 bot 內的下架指令**;不建 DB 收件匣,申請就在信箱裡,維護者定期看信。
  - 確認後在 psql 執行 `SELECT takedown_personnel(<id>);`:同一交易內刪主表 → 清除該醫師的全部歷史 → 寫一筆不含內容的紀錄(OD-8);id 不存在時報錯並回滾。
  - 爬蟲上線時(OD-7),被下架的官網醫師要加入排除清單,避免重爬又加回來;排除清單與「整院下架」在爬蟲 task 一起實作。
  - 2026-10-12 補註:排除清單(`takedown_suppressions`)與整院下架的做法見 OD-10。
  - `search_log` 裡的查詢字串不在下架範圍:它是內部用量資料,不對外顯示,也不關聯到醫師資料列。
- **理由**:
  - 卡片上的按鈕會讓一般使用者誤觸,而且收到申請也無從判斷該不該下架;寄信可以附上證明,維護者能判斷是不是本人或院所。
  - 倫理鐵律 4 要求從第一天就要有下架機制;OD-7 要求在第一批爬蟲資料上線前完成。
  - 用 SQL function 而不是手打三條 SQL:一次做完 OD-8 的三個步驟,不會漏掉清除歷史,也有整合測試(`TestHistoryAllowsTakedownPurge`、`TestTakedownPersonnelRejectsUnknownID`)。

## OD-10 — 官網爬蟲的資料規則(先做亞東)

- **日期**:2026-10-12
- **狀態**:✅ 採納
- **決策**:
  - 先做爬蟲框架+亞東一家,上線跑過一輪正式資料後,再加雙和、長庚、馬偕、國泰(OD-7 第一批)。
  - 每位醫師以「來源:該站醫師 ID」為穩定鍵(`source_key`,例如 `femh:42522`);同一位醫師出現在多個科別只存一筆,科別以「、」串接(最多 100 字)。

- **理由**:
  - 先上一家:比對、刪除、排除清單、歷史這些框架邏輯有問題時只影響一家,修好再擴。
  - 用站內醫師 ID 而不是「姓名+醫院」當鍵:同名醫師常見,醫師換科別也不會被當成另一個人。
  - 查到日期每月更新,卡片上的「查到」才會保持新;若每次都記歷史,5 家每年約多 4 萬筆只改日期的紀錄,真正的變動會被淹沒。
  - 中醫學系也是醫師學位,納入不需要例外規則;卡片照實顯示學歷與科別,判斷留給使用者(倫理鐵律 1)。
  - 刪除保護:網站改版最常見的症狀是「突然抓到 0 筆」,沒有保護就會把整家醫院的資料刪光。
