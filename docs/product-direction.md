# POPO Finder — 產品方向與決策紀錄

> 這份文件記錄一次完整的「產品方向抉擇」討論結論,目的是:**未來真的要動手時,不必再從頭走一次方向選擇。**
> 寫於決策當下;若日後推翻任何一條,請直接改這份文件並註明原因。

---

## 0. 一句話定位

**POPO Finder 是「一本越來越全、越來越準的台灣醫師學歷字典」,不是一個要長成網路效應的平台。**

核心功能:讓一個病人查「這位醫師是台灣醫學系畢業,還是波波?」並得到可信的答案。

---

## 1. 最高決策準則(這把尺凌駕一切)

> **「如果全世界只有 3 個人用,它對那 3 個人還有價值嗎?」**

- 這是一個**自架、不以賺錢為目的、提供真實價值**的 side project(部署在樹莓派上)。
- 因此成功的定義不是「使用者多」,而是「**就算用的人很少,對用的人仍然有價值**」。
- 任何功能在進場前,先用這把尺檢驗。**通不過的,一律延後或不做。**

這把尺的推論:**價值來自「資料覆蓋率 + 正確性」,不是使用者數量。** 心血應投在讓字典更全、更準、更可信 —— 那是「每多一個使用者價值就更高、且不靠別人也成立」的投資,也是抗白工最強的方向。

---

## 2. 為什麼是「字典 / 參考工具」,不是「平台」

最大的擔憂是**做白工**:投入心血做出沒人用的東西。分析後發現:

- 平台類功能(見下方第 4 節)全部是**網路效應**功能 —— 價值要等規模上來才出現。
- 「等規模」恰恰是**白工風險最高**的路:撐過漫長冷啟動之前,產品對任何人都沒用。
- 而「查一位醫師是不是波波」這件事,**不需要任何其他使用者就成立** —— 像查字典,對一個人也有用。
- **這正是現在這個 LINE bot 已經在做的事。** 所謂「擴展」,大多是把產品從「查字典」推向「靠規模」,反而稀釋了它最珍貴的特質。

**結論:核心不要動;擴展的唯一正當目的是「讓字典更全更準」。**

---

## 3. 確定要做 / 保留的方向(通過尺的)

1. **保留核心查詢**:查一位醫師的學歷背景。這是本命,小眾也有價值。
2. **擴展資料覆蓋率**:可以爬更多來源(診所官網、公開學經歷等),但**目的是提高覆蓋率與正確性,不是養網路效應**。
   - 注意:爬診所官網會天然偏向「有行銷意願的自費診所/醫美/牙醫」,覆蓋率有限。**這是特性不是 bug**,接受它。
3. **醫師認領 = 眾包校對(crowdsourced correction),不是成長引擎**。
   - 類比 Google 地圖「建議修改」、維基百科編輯:每一筆修正,讓**下一個查詢的病人**查得更準,完全不需要編輯者之間形成網路。
   - 一個醫師來把自己學歷補對 → 價值立刻兌現給下一個病人。通過尺。

---

## 4. 明確「先不做 / 延後」的方向(通不過尺的)

這些不是壞點子,而是**通不過「3 個人也有價值」這把尺**,或會反過來傷害核心。記錄下來是為了**將來不要又被它們誘惑帶偏**。

| 方向 | 為什麼擱置 |
|---|---|
| **信號/揭露引擎(unraveling)** | 需要醫師密度才會發動,3 個人時完全不動。是成長機制,不是價值機制。 |
| **評價系統(負評)** | ① 威脅**所有**醫師 → 破壞認領/校對意願 ② 在台灣有誹謗 / 醫療法的法律風險。 |
| **評價系統(只放正評)** | **可信度悖論**:病人一旦知道只可能有好評,那些好評就不帶資訊,等同診所自家「見證牆」。付出成本卻換不到可信訊號。 |
| **SEO 讓醫師自己搜到、主動認領** | 要先有流量才成立,網路效應。 |
| **主動發行銷 Email 給爬來的醫師** | ① 樹莓派住宅 IP 寄信幾乎必進垃圾信、可能讓網域被列黑名單 ② 個資法:爬來的 email 作行銷是「目的外利用」紅線 ③ 觀感極差,像詐騙/騷擾。**唯一明確不建議自動化的事。**(真要主動通知,只接受:人工、少量、用公開聯絡管道、語氣是幫忙不是推銷。) |

### 關於「評價」的補充(如果未來真的要做)

- 讓正評有價值的關鍵**不是「擋掉負評」,而是「驗證留評的人真的看過診」**。
  - Google 評價不可信,不是因為它允許負評,而是任何人不用證明看過診就能留。
  - 5 則「已驗證病人」的回饋 > 200 則匿名 —— 而「驗證」剛好是 POPO Finder 的本命能力。
- 三條路裡,**唯一不該做的是中間那條**:「開放大家留、但偷偷只顯示好的」(同時拿到低可信 + 可灌水 + 不誠實)。
  - 誠實的兩條路:① 醫師自選的**見證牆**(明白標示是精選素材) ② **驗證病人的結構化正向回饋**(標籤式,如「解釋清楚」「候診短」)。
- 無論哪條,都是**核心驗證過、資料覆蓋起來之後**才考慮,不是地基。

---

## 5. 不可違背的倫理 / 法律鐵律

即使是 hobby project,這幾條從第一天就要守:

1. **只呈現「已驗證的正面事實」**(學歷、受訓地),**絕不對「缺資料」做任何暗示**。
   - 標示要中性:「已驗證學歷:OO大學」vs「尚未提供」,**不可寫「疑似波波」**。
   - 判斷留給病人自己下,平台不下結論 → 同時避開誹謗與「冤枉沉默者」的倫理陷阱。
2. **定位是「學經歷透明」,不是「抓波波」。**
   - 陳述事實(在哪受訓、學歷已驗證)= 可受法律保護;暗示判斷(波波=爛)= 訴訟磁鐵,且前提本身有爭議(所有執業醫師都通過國考)。
3. **誠實標示驗證程度**:爬來的 / 醫師自填 / 已驗證,要分清楚,不可過度宣稱。
4. **從第一天就要有「主動下架機制」** —— 把別人公開資料搬上來的安全閥。診所/醫師要求下架要能照辦。
5. **認領流程不可變成「資料當人質」的勒索感**(那種「我有你的資料,想控制就來求我」的人肉搜索套路)。要先給真實善意:免費好頁、自證機會、隨時可下架。

---

## 6. 對技術架構的意涵(摘要,細節待真的要做時再展開)

- **現況**:Go 單體 + chi + sqlx/pgx + Postgres,單一 `medical_personnel` 表,資料來自波波一覽表 blog,介面只有 LINE webhook bot。**這個「查字典」的形狀本身就是對的**,不需要重寫。
- **若要做眾包校對(醫師認領)**:需要新增「網頁」介面(server-render HTML 路由,同一個 Go binary 即可),以及 schema 上區分**資料來源 / 驗證狀態 / 認領狀態**的欄位,加一張「認領/校對意願」收件匣表(初期可 Wizard-of-Oz 人工處理)。
- **但這些都等方向上想做眾包校對時再動**;目前的 MVP 判斷是「**還太早,先把方向釘死**」(本文件)。

---

## 7. 仍未解、之後要面對的問題

- **驗證的可信度**:自填學歷零可信;能驗證的頂多是「這是醫師本人具名揭露」,而非「這份學歷一定為真」。要如何在介面上誠實表達這個程度?
- **資料時效**:醫師會跳槽、診所會倒,爬來的資料數月就過期;過期資料比沒資料更傷信任。更新機制怎麼設計?
- **波波資料的根本限制**:政府不公開誰是波波,負面資料爬不到 —— 所以長期仍要靠「正面揭露 / 校對」把字典補全。這個 bootstrap 怎麼啟動?

---

## 附:這次討論的演進軌跡(濃縮)

1. 最初想法:擴成「全台醫師資料 + 評價 + 醫師認領做形象頁」的平台。
2. 釐清目標:**不為賺錢**,只想在樹莓派上部署一個有人用、提供價值的服務。
3. 發現核心矛盾:「對病人有價值的資訊(波波、負評)」與「需要醫師自願貢獻的成長引擎」**天生打架**。
4. 第一次收斂:砍負評 → 定位「學歷透明」而非「評價平台」。
5. 細修:正評不像負評那樣傷引擎,但有**可信度悖論**;真正的槓桿是「驗證留評者」。
6. **最終定盤**:祭出「3 個人也有價值」這把尺 → 發現平台類功能全通不過 → **重新定位為「醫師學歷字典 / 參考工具」**,擴展的唯一目的是資料覆蓋與正確性,認領降格為眾包校對。**這是目前的最終方向。**
